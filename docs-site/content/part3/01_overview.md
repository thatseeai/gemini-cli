## 이 파트에 대하여

Gemini CLI를 사용할 때 많은 사용자들이 "이건 AI가 한 건가, 프로그램이 한 건가?"라는 의문을 가집니다. 3부에서는 LLM(Gemini API)과 Agent(Gemini CLI)의 역할을 명확히 구분하여, 각 기능이 실제로 어디서 처리되는지 사용자 관점에서 설명합니다.

## LLM과 Agent의 기본 역할

### LLM (Large Language Model - Gemini API)의 역할

LLM은 **"두뇌"** 역할을 합니다.

**주요 책임**:
- 사용자 의도 이해
- 작업 계획 수립
- 도구 선택 결정
- 자연어 응답 생성
- 코드 이해 및 분석
- 추론 및 판단

**LLM이 하는 것**:
```
사용자: "README.md 파일을 읽어줘"

LLM의 사고 과정:
1. 사용자가 파일 읽기를 원함 → 의도 파악 ✓
2. 'read-file' 도구가 필요함 → 도구 선택 ✓
3. 파일 경로는 "README.md" → 파라미터 결정 ✓
4. read-file(file_path="README.md") 호출 결정 → 함수 호출 ✓
```

**LLM이 하지 않는 것**:
- 실제 파일 읽기 (파일 시스템 접근 불가)
- 셸 명령 실행
- 네트워크 요청
- 상태 저장
- 도구 실행

### Agent (Gemini CLI)의 역할

Agent는 **"손과 발"** 역할을 합니다.

**주요 책임**:
- 도구 실행
- 파일 시스템 조작
- 셸 명령 실행
- 히스토리 관리
- 컨텍스트 유지
- 사용자 확인 처리
- 에러 처리 및 재시도
- 보안 정책 적용

**Agent가 하는 것**:
```
LLM 요청: read-file(file_path="README.md")

Agent의 실행 과정:
1. 도구 레지스트리에서 'read-file' 조회 ✓
2. 파라미터 검증 (file_path 존재 여부) ✓
3. 정책 엔진에 확인 (자동 허용/거부/사용자 확인) ✓
4. 실제 파일 시스템에서 README.md 읽기 ✓
5. 결과를 LLM이 이해할 수 있는 형식으로 변환 ✓
6. 히스토리에 기록 ✓
```

**Agent가 하지 않는 것**:
- 어떤 도구를 사용할지 결정
- 파일 내용 해석 및 요약
- 다음에 무엇을 할지 계획
- 자연어 응답 생성

## 협업 모델

LLM과 Agent는 **협업**하여 작업을 완수합니다.

```
사용자 요청
    ↓
[Agent] 요청을 LLM에 전달
    ↓
[LLM] 의도 파악 및 계획 수립
    ↓
[LLM] 도구 호출 결정
    ↓
[Agent] 도구 실행 및 결과 수집
    ↓
[Agent] 결과를 LLM에 전달
    ↓
[LLM] 결과 해석 및 응답 생성
    ↓
[Agent] 응답을 사용자에게 표시
```

## 구체적인 예제

### 예제 1: 파일 읽기

**사용자**: "README.md 파일을 읽고 요약해줘"

| 단계 | 담당 | 작업 |
|-----|------|------|
| 1. 의도 파악 | **LLM** | "파일 읽기 + 요약" 두 작업 필요 |
| 2. 계획 수립 | **LLM** | 먼저 read-file, 그 다음 내용 요약 |
| 3. 도구 선택 | **LLM** | read-file 도구 선택 |
| 4. 파라미터 결정 | **LLM** | file_path="README.md" |
| 5. 함수 호출 요청 | **LLM** | read-file(file_path="README.md") |
| 6. 요청 수신 | **Agent** | Function Call 이벤트 파싱 |
| 7. 정책 확인 | **Agent** | read-file은 안전 → 자동 허용 |
| 8. 파일 읽기 | **Agent** | fs.readFile("README.md") 실행 |
| 9. 결과 반환 | **Agent** | 파일 내용을 FunctionResponse로 변환 |
| 10. 내용 이해 | **LLM** | 파일 내용 분석 |
| 11. 요약 생성 | **LLM** | 핵심 내용 추출 및 요약 작성 |
| 12. 응답 출력 | **Agent** | LLM 응답을 터미널에 표시 |

**결과**:
```
README.md 파일을 읽었습니다. 이 프로젝트는 'My Project'라는 이름으로,
TypeScript로 작성된 웹 애플리케이션입니다. 주요 기능은 사용자 인증과
데이터 시각화입니다. 설치는 `npm install` 명령으로 할 수 있으며,
개발 서버는 `npm run dev`로 실행할 수 있습니다.
```

- **Agent가 한 일**: 파일 읽기
- **LLM이 한 일**: 파일 내용 이해 및 요약

### 예제 2: 코드 수정

**사용자**: "src/utils.ts에서 processData 함수에 에러 처리를 추가해줘"

| 단계 | 담당 | 작업 |
|-----|------|------|
| 1. 의도 파악 | **LLM** | 특정 함수에 에러 처리 추가 |
| 2. 계획 수립 | **LLM** | 1) 파일 읽기 → 2) 함수 찾기 → 3) 코드 수정 |
| 3. 파일 읽기 요청 | **LLM** | read-file(file_path="src/utils.ts") |
| 4. 파일 읽기 실행 | **Agent** | 실제 파일 읽기 |
| 5. 코드 분석 | **LLM** | processData 함수 위치 및 구조 파악 |
| 6. 수정 계획 | **LLM** | try-catch 추가, 입력 검증 추가 |
| 7. 수정 코드 생성 | **LLM** | 새로운 코드 작성 |
| 8. edit 도구 호출 | **LLM** | edit(file_path, old_string, new_string) |
| 9. 사용자 확인 | **Agent** | 파일 수정 확인 프롬프트 표시 |
| 10. 확인 대기 | **Agent** | 사용자 입력 대기 |
| 11. 파일 수정 | **Agent** | 실제 파일 쓰기 |
| 12. 결과 확인 | **LLM** | 수정 완료 메시지 생성 |

**결과**:
```
processData 함수에 에러 처리를 추가했습니다:
- 입력 검증 (빈 문자열 체크)
- try-catch 블록으로 예외 처리
- 에러 발생 시 로깅
```

- **Agent가 한 일**: 파일 읽기, 사용자 확인, 파일 수정
- **LLM이 한 일**: 코드 분석, 수정 계획, 새 코드 생성

### 예제 3: 복잡한 분석

**사용자**: "이 프로젝트의 테스트 커버리지가 어느 정도인지 분석해줘"

| 단계 | 담당 | 작업 |
|-----|------|------|
| 1. 의도 파악 | **LLM** | 테스트 커버리지 분석 필요 |
| 2. 계획 수립 | **LLM** | 1) 테스트 파일 찾기 → 2) 커버리지 도구 확인 → 3) 분석 |
| 3. 패키지 확인 | **LLM** | read-file(file_path="package.json") |
| 4. 파일 읽기 | **Agent** | package.json 읽기 |
| 5. 스크립트 분석 | **LLM** | 커버리지 스크립트 존재 여부 확인 |
| 6. 커버리지 실행 | **LLM** | shell(command="npm run test:coverage") |
| 7. 명령 확인 | **Agent** | 셸 명령 실행 확인 프롬프트 |
| 8. 명령 실행 | **Agent** | 실제 npm 명령 실행 |
| 9. 출력 수집 | **Agent** | 커버리지 리포트 수집 |
| 10. 결과 해석 | **LLM** | 커버리지 수치 분석 |
| 11. 보고서 작성 | **LLM** | 분석 결과 정리 및 개선 제안 |

**결과**:
```
테스트 커버리지 분석 결과:

전체 커버리지: 78.5%
- Statements: 82.3%
- Branches: 71.2%
- Functions: 85.1%
- Lines: 78.5%

커버리지가 낮은 파일:
- src/auth/oauth.ts (45.2%)
- src/utils/validation.ts (52.8%)

권장 사항:
1. 인증 관련 로직의 테스트 강화
2. 유효성 검증 함수의 엣지 케이스 테스트 추가
```

- **Agent가 한 일**: 파일 읽기, 셸 명령 실행, 출력 수집
- **LLM이 한 일**: 분석 계획, 결과 해석, 보고서 작성, 개선 제안

## 핵심 원칙

### 1. 판단은 LLM, 실행은 Agent

```
❌ 잘못된 이해:
"Gemini CLI가 파일을 읽고 요약한다"

✓ 올바른 이해:
"LLM이 파일 읽기를 결정하고, Agent가 파일을 읽고,
 LLM이 내용을 요약한다"
```

### 2. LLM은 상태가 없음

```
❌ 잘못된 이해:
"LLM이 이전 대화를 기억한다"

✓ 올바른 이해:
"Agent가 히스토리를 저장하고 매번 LLM에 전달한다"
```

### 3. Agent는 판단하지 않음

```
❌ 잘못된 이해:
"Gemini CLI가 스스로 다음에 무엇을 할지 결정한다"

✓ 올바른 이해:
"LLM이 다음 행동을 결정하고, Agent는 그것을 실행한다"
```

### 4. 도구는 Agent의 능력

```
❌ 잘못된 이해:
"LLM이 파일을 수정할 수 있다"

✓ 올바른 이해:
"LLM은 파일 수정 도구 사용을 요청하고,
 Agent가 실제로 파일을 수정한다"
```

## 책임 분리의 이점

### 1. 명확한 역할 구분
- LLM: 지능적 판단
- Agent: 안전한 실행

### 2. 보안
- Agent가 정책 엔진으로 위험한 작업 제어
- LLM은 직접적인 시스템 접근 불가

### 3. 확장성
- 새로운 도구 추가 시 LLM 재학습 불필요
- Agent만 업데이트하면 됨

### 4. 디버깅 용이성
- 판단 오류: LLM 프롬프트 개선
- 실행 오류: Agent 코드 수정

### 5. 투명성
- 사용자가 각 단계를 확인 가능
- LLM의 결정과 Agent의 실행을 구분하여 표시
